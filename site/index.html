A modern server for Ring apps,
web services, and what comes next.

Where RingScript makes Ring resident in the browser, RingServ makes it resident on the server: one static binary that speaks HTTP by web standards, runs your services in beautiful declarative Ring — or in JavaScript — stores data in embedded SQLite, and syncs with local-first RingScript pages. No Apache, no npm, no runtime to install, nothing to configure.

The same service, two ways

A greeting endpoint: read a name, default it, answer politely. Below are the two versions of the very same service — line for line, same length, same order — so the only thing that differs is how the logic reads.

The JavaScript version starts from npm install express and a node_modules directory; the Ring version starts from one downloaded file.

Node + Express 13 lines
require the framework, wire the route, parse the body 
const express = require("express")
const app = express()
app.use(express.json())

app.post("/api/greet", (req, res) => {
    let name = req.body.name
    if (!name) { name = "stranger" }

    res.json({
        message: "Ahlan, " + name + "!"
    })
})
app.listen(8080)
Ring 13 lines
declare the service, name the action, say what you mean 
RingServ([
    :port = 8080,
    :services = [
        :hello = [
            :greet = func aReq {
                cName = aReq[:payload][:name]
                if cName = "" cName = "stranger" ok
                return Reply(:ok, [
                    :message = "Ahlan, " + cName + "!" ])
            }
        ]
    ]
])

No routes to design, no verbs to choose, no body parser to remember: every service answers at /api/v1 as service.action(payload) — the same call shape RingScript pages already speak. That is the whole trick — and it holds as the application grows.

What you get

◉

A whole backend in one file

The web server, the Ring VM, a SQL database and a JavaScript engine, compiled into one static binary per platform. Install is: download it, run it.

◈

Errors that don't kill the server

A mistake in a service returns a clean answer with its real line number, and the server keeps serving. Thousands of hostile requests later, memory is still flat.

⇆

Two languages, one application

A service can be a .js file. It follows the same rules as a Ring one, and each side calls the other by name. The seam is thin — and optional.

❐

A database already inside

Describe your tables, write ordinary SQL, and say what each request must contain — bad requests are turned away before your code ever sees them.

⧉

History that cannot be edited

A journal you can only add to. Each entry is sealed with a fingerprint of the one before it — if anyone edits the past, the server points at exactly where.

✦

Pages that work offline

Declare where each service and table lives — page, server, or both with sync. Move one between them by changing a word, not the application.

What people build with it

The reason this exists: business applications whose rules keep working when the connection does not. The reference application is a café counter — orders taken, sent to a kitchen, paid for, and written into a sales record that can never be quietly altered — wiring every service form together the way a real application does.

The interface stays plain HTML and CSS, served by the same binary. Your pages can stay in RingScript — the browser sister that speaks the same call(service.action, payload) — and what runs on the server is the part that decides: pricing, stock, the fiscal record.

Three steps, no ceremony

  1. Get the one file. Download it from the releases page for Linux, macOS or Windows — or scaffold a working app with ringserv new myapp --gesture.
  2. Serve it. ringserv serve myapp.ring publishes your functions; ringserv dev watches and reloads while you work. Settings live in a small plain-text ringserv.yaml beside your code.
  3. Grow it. When functions are not enough, declare tables, contracts, a journal and placement — the tutorial walks the whole arc in six runnable steps.

One programming model, two players

RingServ and RingScript are two halves of one idea. A page calls serv.call("orders.place", {...}); a server declares :orders with a :place action. The call shape is identical on both sides, so a fullstack application declares its services and its data once, and a separate declaration — the topology — decides where each piece lives: in the page, on the server, or on both with sync.

The consequence is the one-word move: a pricing rule that must work offline runs in the page; the day it needs the whole dataset, change :site = :local to :site = :server and deploy. The rule's code does not change, the page's call does not change — only the answer's journey does. No other pairing we know of — Node and its frameworks included — lets the same declaration move between browser and server untouched.

And the losses are published with the wins

The benchmarks exist to find the headroom, not to win an argument — so every cost is on the record next to every number, with its cause. The causes became the work.

What the numbers say

  • A full service round trip — 0.75 ms, against a 0.26 ms floor for a request that never enters the VM
  • A write costs about a read — 0.94 vs 0.78 ms, because every write rides one well-planned transaction
  • The JavaScript guest is not slower — 0.69 ms against Ring's 0.75 for the same action
  • Peak throughput — 5,669 requests/s at twenty in flight, on four workers

And what it cost to learn

  • The naive way to write that transaction cost 10.13 ms — thirteen times the final figure — and the difference is documented, not assumed
  • Listing 500 rows is bound by JSON encoding, not by the database — the codec was rewritten in C after it showed up at 1,134 ms on a 2,000-row reply
  • An early sweep hit a concurrency cliff: fine to 18 in flight, then collapse. Finding it changed the connection handling; the write-up kept the cliff

Honest limits

For HTTPS, put a proxy in front. RingServ speaks plain HTTP on purpose — encryption libraries are large and change often, and copying one in would break the promise that the binary has no dependencies. Caddy, nginx or Traefik handle certificates in a few lines, and RingServ refuses to start on a public address until you confirm one is there, so traffic cannot go out in the clear by accident.

Two features cover the common cases and say so: number formatting in JavaScript supports eight languages and nine currencies, and ringserv.yaml reads ordinary settings rather than the whole YAML standard. Step outside either and you get a clear error naming what is missing — it never guesses and gets it quietly wrong. And 0.9 means ready to use, not finished: everything here works and is tested, but a command may still change before 1.0.
