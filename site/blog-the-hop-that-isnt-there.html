The hop
that isn't there.

Position · 2026-08-29 · The industry has started naming something RingServ was already built as: data, compute and messaging in one process, with no network between them. Here is the measurement that supports it — taken on RingServ, by RingServ — and the four things it honestly does not buy.

A paradigm got a name

In August 2026 InfoQ reported a benchmark from Harper, arguing that collapsing the usual tiers — an application process talking over a network to a database, a cache and a message broker — into a single runtime is worth several times the latency on live, personalized data. Their published figures: about 0.4 ms in-process against ~3 ms across the network, and up to ~14× on the paths where the data is genuinely per-user and cannot be cached.

It is a vendor benchmarking its own architecture, and it should be read that way. To their credit, the caveats are published with it: the dataset was warm and in memory, and the serverless stack wins on cacheable content, broadcast workloads and high fan-out. Those are real losses, honestly stated. We will state ours further down.

We are writing about it because the argument is one RingServ made from first principles before anyone was selling it — not as a performance strategy, but as a consequence of a much simpler goal: one file to download, nothing to install.

What "in one process" actually means here

RingServ is a single static binary. The Ring VM, SQLite, the QuickJS-ng JavaScript engine and the web server are compiled into the same executable and run in the same address space. The result is not a fast database call. It is the absence of a database call, in the sense a tiered stack means it:

❐

The data

A query reaches SQLite through a function call. No socket, no wire protocol, no connection pool, no serializing the query out and the rows back.

⧉

The record

The append-only journal — the history nobody can quietly edit — is in the same file, on the same connection discipline as everything else.

⇆

The messaging

A page that subscribes is held as state in this server, not routed through a broker somewhere else. No third system to run, secure and pay for.

◉

The other language

A JavaScript service is not a separate runtime either. It is resident too, and calling a Ring service from it costs one extra dispatch — measured.

The number that decomposes the claim

Here is the part worth having, and RingServ measured it on itself long before the paradigm had a name. The same service dispatch, called two ways on the same server — once over HTTP, once directly in the process:

0.72 ms

11%
of a request is actually Ring

Nine times, and it is the same shape Harper published as 0.4 against 3 — different hardware, different stacks, same cause: a socket, a queue and a thread handoff cost about an order of magnitude more than a function call. What makes our version of the measurement useful is that both sides of it are the same server. There is no second product's tuning hiding in the comparison.

It supports one precise sentence, and it has been in our benchmarks document for months: Ring is 11% of a request; the other 89% is the HTTP layer and the handoff to a worker. That is the entire fusion argument stated as an engineering fact instead of a slogan — every hop you remove is worth roughly that much. RingServ removed the database hop completely, which is why a create costs 0.91 ms including HTTP, dispatch, contract validation and a real durable commit — where a tiered stack's three milliseconds is the hop before any of that work begins.

One honest footnote, because it is the more useful half: that same create cost 10.13 ms here until the one-writer connection landed on 17 August 2026. Being in one process did not make it fast. Being in one process and getting the connection discipline right made it fast — and the second half was work.

What it buys, and what it does not

House rule: the losses go beside the wins, on the same screen, at the same size. A benchmark that shrinks its own losses is an advertisement.

What co-location genuinely buys

  • The database hop is gone, not optimized — there is no socket to tune, no pool to size, no serialization on the path.
  • A durable write, end to end over HTTP, in 0.91 ms — contract validation and commit included.
  • Nothing to assemble: no broker, no cache tier, no ORM, no node_modules. The supply-chain audit is one pinned list.
  • Boot to first answer in 228 ms, from a ~7 MB file.

What it does not buy

  • A fast engine. Against plain node:http, Node wins every row we publish — 2.1×, 2.9×, 2.2×. Removing hops does not close an engine gap.
  • The client hop. That 89% is our own HTTP transport. Every architecture pays it, and quoting in-process latency as if it were end-to-end is quoting the half of the journey you like.
  • Freedom from the working set. Past SQLite's page cache it is disk I/O. We degrade down a slope rather than off a cliff — but we have not measured that at scale, so we do not claim it.
  • Elastic fan-out. Peak here is ~5,700 reads/s on one machine, and scaling flattens past four workers. Our answer to growth is declared placement, not autoscaling.

The failure mode that arrives with it

Every architectural property you gain brings a failure mode wearing that property's own clothes. This one is worth naming because we paid for it — on 2026-08-28, the day before this article.

When the database is a separate tier, "can I reach it?" is a connection question, asked continuously by a pool that retries. When data and compute are one process, it quietly becomes a boot question about the process itself — and a process that answers it wrong looks perfectly healthy from outside.

Which is exactly what ours did. A worker whose database could not be reached — a read-only file, a directory that did not exist — marked itself alive anyway. The server printed serving on http://..., answered its health check with a cheerful 200, and failed every request that touched data, indefinitely, with nothing in between to say why. It is fixed at both points now: a worker that cannot reach its database refuses and names the reason, and the server refuses to start at all if no worker ever came up. There is a test suite whose only job is to keep it that way.

We are telling you about a bug in an article about an architecture we like, because the alternative is an architecture you cannot calibrate.

What we are not going to do about it

Nothing. No in-memory table type, no bundled cache tier, no broker — none of the shopping list a paradigm tends to arrive with. RingServ's data layer is plain SQL over the most-deployed database in the world, journaled, with none of its own persistence inventions, and that is the property worth protecting.

This project settled that instinct once already, by deletion: there is no framework query dialect here, because plain SQL was the better answer and removing the idea was the better move. The same applies to a validated trend. The right response to the industry agreeing with you is to write down what you can prove, publish what you cannot, and keep building.
